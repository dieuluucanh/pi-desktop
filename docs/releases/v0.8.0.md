# Pi Desktop v0.8.0

**Release date:** 2026-11-08 · **Status:** published to GitHub Releases by
`.github/workflows/release.yml` on tag `v0.8.0` · **Pi SDK:**
`@earendil-works/pi-coding-agent` 1.4.0 · **Bundled runtime:** Node 24.22.2

Pi Desktop is a standalone desktop app for the [Pi coding agent](https://pi.dev):
projects, sessions, chat, providers, models, extensions, packages, skills, themes and
settings in a UI, using the **same `~/.pi/agent` profile as terminal Pi**, so the two are
interchangeable. **Pi for Office is an optional integration**, not a built-in surface.

This is the fourth public release. The headline is a **notifications and updates
refactor**: notifications now have classes, the bell is a real bell with a count and a
closeable popover, and a newer release is offered as an ordinary notification instead of
a status-bar chip. **About & updates** left Settings and became its own view at the
bottom of the sidebar, where it can also carry the update dot.

## Install

Download from [GitHub Releases](https://github.com/dieuluucanh/pi-desktop/releases).

| Platform      | Artefacts                                                                                                            | Status  |
| ------------- | -------------------------------------------------------------------------------------------------------------------- | ------- |
| Windows (x64) | `Pi-Desktop-0.8.0-win-x64-setup.exe` (NSIS), `Pi-Desktop-0.8.0-win-x64-portable.exe`                                 | primary |
| Linux         | `Pi-Desktop-0.8.0-linux-x86_64-appimage.AppImage`, `Pi-Desktop-0.8.0-linux-amd64-deb.deb` (x64) and the `arm64` pair | beta    |
| macOS         | `Pi-Desktop-0.8.0-mac-arm64.dmg`, `Pi-Desktop-0.8.0-mac-x64.dmg` (plus the `.zip` pair used by the updater)          | beta    |

Builds are **unsigned**. Windows SmartScreen warns on first launch (**More info → Run
anyway**). macOS additionally requires an explicit approval:

1. Open the `.dmg` and drag **Pi Desktop** into `/Applications`.
2. Launch it once. macOS refuses, and there is no right-click override any more.
3. Open **System Settings → Privacy & Security**, scroll to the bottom, and choose
   **Open Anyway** for Pi Desktop.

If the bundle reports that it is **damaged** instead (usually after unzipping the `.zip`
rather than mounting the `.dmg`), clear the quarantine flag and try again:

```bash
xattr -dr com.apple.quarantine "/Applications/Pi Desktop.app"
```

On Linux, the AppImage needs FUSE (`libfuse2`, or run with `--appimage-extract-and-run`);
install the `.deb` with `sudo apt install ./…deb` rather than `dpkg -i` so the
GTK/NSS/asound dependencies resolve. The app bundles its own Node runtime: no system
Node, npm or Pi install is needed.

## Updates

| Platform         | In-app check           | In-app install                                 |
| ---------------- | ---------------------- | ---------------------------------------------- |
| Windows          | yes, 10 s after launch | yes — download, then **Restart & install**     |
| Linux (AppImage) | yes                    | yes                                            |
| macOS            | **no**                 | **no** — download the new `.dmg` from Releases |

macOS updates stay download-only: Squirrel.Mac validates a downloaded update against
the running app's code-signing requirement, and an ad-hoc signature's requirement
changes with every build. **About & updates** says **Manual updates** and links to the
Releases page. A Developer ID certificate (or a stable self-signed release certificate)
is what turns this back on.

v0.7.3 was the first published 0.7 build; v0.8.0 is the version an installed v0.7.3
build should pick up. Windows and the Linux AppImage are the targets; macOS stays
manual.

## What changed since v0.7.3

### Notification classes

`ctx.ui.notify(message, type)` carries no extension/source field, so the app classifies
notifications by **severity plus one app-owned kind**: `update`, `error`, `warning` and
`info`. Settings → Notifications switches each class on or off. Updates, errors and
warnings start **on**; informational messages start **off**, so background chatter such
as "Server logs ready (local)" no longer fills the bell or the transcript. There are
deliberately no content heuristics.

A hidden notification is **archived, not deleted**. The popover's **Show hidden (N)**
toggle reveals suppressed rows with `hidden` / `muted` badges, **Show class** enables a
disabled class, and **Unmute** removes a matching rule. The transcript filters at render
time, so enabling a class restores its notice rows without a reload. The archive is
still bounded to 100 rows.

Per-message mute rules remain the fine-grained layer, with three scopes: the exact text,
a template signature, or a whole type. The **warnings like this** (template) option is now
always selectable; when the message has no variable parts the dialog says that rule
matches the same text as the exact one instead of disabling it.

### The bell is a bell

The old text button labelled `notifications <count>` is gone.

- The status bar always renders a bell, even with nothing to show, so notification
  settings and the hidden archive stay reachable.
- The count badge covers **unsuppressed** rows only, turns danger-tinted when a visible
  error is present, and caps at `99+`.
- The popover has an explicit **×** close control, a per-row **×**, **Clear**, a class
  badge per row, the **Show hidden (N)** footer and a **Notification settings** link that
  opens Settings focused on the Notifications card.
- Warning and error toasts keep their gear (mute dialog). Info notifications still never
  toast.

### The update offer is a notification

An automatic check that finds a newer release now raises exactly **one** app-owned
notification for that version, class `update`, with a **View update** action. Its toast
carries the same action. `prefs.updates.notifiedVersion` records the version already
announced: a repeated push, a manual re-check or a relaunch does not raise it again, a
new version does, and **Notify me again** in the view clears the marker and re-raises it.
The old `dismissedVersion` key is dropped by the preferences sanitizer, so no migration
is needed.

There is **no status-bar update chip** and no OS-level notification. Instead the
**About & updates** sidebar item carries a dot while a version is available
(accent), downloading (info) or ready (ok); the dot is an availability indicator, not a
notification, so dismissing the row does not remove it. Automatic failures stay silent;
a manual check still reports up-to-date, no-feed and error outcomes as a dismissible
status hint plus the view.

### About & updates is its own view

App identity and the updater were the last card in Settings, which is the wrong home for
them. **About & updates** is now the last sidebar item, below Diagnostics, and the
Settings card is gone. The view carries build channel/version/commit, update status,
download progress, **Download** and **Restart & install**, the automatic-check switch,
release notes, the raw updater error under **Technical details**, and a link to the
Releases page. `Help → Check for Updates…`, `Help → About Pi Desktop` (Windows/Linux),
`Go → About & Updates` and the command palette all open it. macOS keeps its native
About panel.

The packaged updater offer against a **live published feed** was not exercised by hand
for this release; the offer/announce-once logic is covered with a fake updater port and
staged update states. The Windows installer remains the primary manual path and should
be walked before the release is announced as hand-verified.

**Verified structurally, not on a live machine** for macOS: no Mac was available, so the
bundles are CI-verified but have never been launched by a person. Linux is in the same
position as before — built and inspected on a real Ubuntu host, but not installed on a
desktop by a person for this release.

## Known limitations

- **Unsigned builds.** Windows SmartScreen and macOS Gatekeeper warn on first launch, and
  macOS requires the System Settings approval described above. Code signing and
  notarization need an Apple Developer Program membership and a Windows certificate; both
  are backlog items.
- **macOS and Linux are beta.** **Verified structurally, not on a live machine** on
  macOS, and not re-verified by hand on a Linux desktop for this release. Windows remains
  the primary, hand-verified platform.
- **macOS updates are manual** until a stable signing identity exists (see above).
- **The update offer is in-app only.** There is no OS-level notification, no tray badge
  and no full-width banner; delivery is the bell, the toast and the sidebar dot. One
  notification is raised per offered version, and dismissing it does not clear the dot —
  use **Notify me again** in About & updates, or wait for a newer version.
- **Informational notifications start hidden.** A useful `info` message — including the
  app's own checkpoint confirmations — needs the **Informational messages** class enabled
  in Settings → Notifications. Hidden rows are never lost: **Show hidden (N)** recovers
  them.
- **The terminal needs a real PTY.** It is a local shell only: no remote/SSH session, no
  tmux control mode, no session recording and no docked split panel. Terminals in an
  untrusted project do not spawn until you grant trust, and a terminal tab holds one
  shell.
- **Linux arm64 needs node-gyp at release time.** There is no upstream `node-pty`
  prebuild for Linux, so the arm64 job compiles on an arm64 runner.
- **AppImage updates** require the desktop to set `APPIMAGE`, which is standard for
  AppImageLauncher and most menus but not universal; the `.deb` install never
  self-updates.
- **Nested repositories stay invisible in Changes.** Deliberate, documented parity with
  VS Code; the Explorer still sees them.
- **i18n, MCP and multi-window** remain deferred backlog, as recorded in
  [`product/backlog.md`](../product/backlog.md).

## Upstream

The app pins `@earendil-works/pi-coding-agent` 1.4.0 and ships Node 24.22.2 as its
bundled runtime. Pi's `SettingsManager`/`SessionManager` write non-atomically, so a crash
during Pi's own flush can truncate `settings.json` or a session JSONL; the pinned SDK
cannot be patched. All SDK contact stays in `src/host/sdk/*`, which is what keeps an
upgrade to one directory. The terminal host deliberately imports no SDK code and is a
separate build input.
