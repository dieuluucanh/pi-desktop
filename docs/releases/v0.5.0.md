# Pi Desktop v0.5.0

**Release date:** 2026-11-04 · **Status:** first public release; published to GitHub
Releases by `.github/workflows/release.yml` on tag `v0.5.0` · **Pi SDK:**
`@earendil-works/pi-coding-agent` 1.4.0 · **Bundled runtime:** Node 24

Pi Desktop is a standalone desktop app for the [Pi coding agent](https://pi.dev):
projects, sessions, chat, providers, models, extensions, packages, skills, themes and
settings in a UI, using the **same `~/.pi/agent` profile as terminal Pi**, so the two are
interchangeable. **Pi for Office is an optional integration**, not a built-in surface.

This release is about distribution rather than features. The repository is now public,
and the app is built and published from CI for **all three platforms** — including
macOS, which had never been packaged before. Installers and their `electron-updater`
manifests are uploaded to a draft GitHub Release by three platform jobs and published only
when all three succeed, so the first live update feed is complete the moment it exists.
Application code is unchanged from the local v0.4.0 build apart from one user-visible
policy described below.

## Install

Download from [GitHub Releases](https://github.com/dieuluucanh/pi-desktop/releases).

| Platform      | Artefacts                                                                                                            | Status  |
| ------------- | -------------------------------------------------------------------------------------------------------------------- | ------- |
| Windows (x64) | `Pi-Desktop-0.5.0-win-x64-setup.exe` (NSIS), `Pi-Desktop-0.5.0-win-x64-portable.exe`                                 | primary |
| Linux         | `Pi-Desktop-0.5.0-linux-x86_64-appimage.AppImage`, `Pi-Desktop-0.5.0-linux-amd64-deb.deb` (x64) and the `arm64` pair | beta    |
| macOS         | `Pi-Desktop-0.5.0-mac-arm64.dmg`, `Pi-Desktop-0.5.0-mac-x64.dmg` (plus the `.zip` pair used by the updater)          | beta    |

Builds are **unsigned**. Windows SmartScreen warns on first launch (**More info → Run
anyway**). macOS additionally requires an explicit approval, and the flow differs from
older guides:

1. Open the `.dmg` and drag **Pi Desktop** into `/Applications`.
2. Launch it once. macOS refuses, and there is no right-click override any more.
3. Open **System Settings → Privacy & Security**, scroll to the bottom, and choose
   **Open Anyway** for Pi Desktop.

If the bundle reports that it is **damaged** instead (usually after unzipping the `.zip`
rather than mounting the `.dmg`), clear the quarantine flag and try again:

```bash
xattr -dr com.apple.quarantine "/Applications/Pi Desktop.app"
```

On Linux, the AppImage needs FUSE (`libfuse2`, or run with
`--appimage-extract-and-run`); install the `.deb` with `sudo apt install ./…deb` rather
than `dpkg -i` so the GTK/NSS/asound dependencies resolve. The app bundles its own Node
runtime: no system Node, npm or Pi install is needed.

## Updates

| Platform         | In-app check           | In-app install                                 |
| ---------------- | ---------------------- | ---------------------------------------------- |
| Windows          | yes, 10 s after launch | yes — download, then **Restart & install**     |
| Linux (AppImage) | yes                    | yes                                            |
| macOS            | **no**                 | **no** — download the new `.dmg` from Releases |

macOS updates are download-only by design in this release. Squirrel.Mac validates a
downloaded update against the running app's code-signing requirement, and an ad-hoc
signature's requirement changes with every build, so an in-app install would always fail.
Rather than offer a button that cannot work, **Settings → About & updates** says
**Manual updates**, explains where updates come from, and links to the Releases page. A
Developer ID certificate (or a stable self-signed release certificate) is what turns this
back on; both are recorded in the backlog.

## What changed since the local v0.4.0 build

- **A tag now builds and publishes everything.** `v0.5.0` runs three GitHub Actions jobs
  — Windows, Linux, macOS — which build on their own OS, assert the finished artefacts,
  and upload installers plus `latest*.yml` to a draft release. A final job publishes it
  only when all three passed, then re-reads the feed anonymously to prove it serves.
- **macOS artefacts exist for the first time**, arm64 and x64, ad-hoc signed, with CI
  checking the signature, the bundled runtime, the packaged `pi` shim and the provenance
  file inside the `.app`.
- **The update feed is live.** Installers are stamped `channel: "release"` and
  `electron-updater` reads GitHub Releases anonymously (the repository is public).
- **One user-visible change:** macOS reports manual updates instead of offering an
  in-app install that would fail.
- Local `package:mac` / `package:linux` now regenerate the host shims and run
  `runtime:verify`, so a fresh clone cannot package an unverified runtime.

## Verification status

Automated (green on the release commit):

- `npm run format:check`, `typecheck`, `lint`, `npm test`, `npm run build`,
  `npm run runtime:verify`, `office:manifest:check`, extension package gate.
- Per-platform release jobs: Windows (NSIS + portable + blockmap + `latest.yml`), Linux
  (AppImage + deb for x64/arm64, `dpkg-deb` metadata and contents, two manifests), macOS
  (both `.app` bundles: `codesign --verify --deep --strict`, `spctl` rejecting only for a
  missing Developer ID, the packaged `pi`/node binaries running from inside the bundle,
  and `build-info.json` reporting `release` + `adhoc`).
- The publish job fetches all four manifests and one installer per platform back from the
  public internet without a token.

Manually verified on this release: the Windows installer, installed from the published
URL, reports the release channel and **Check now** answers "up to date".

**Verified structurally, not on a live machine** for macOS: no Mac was available, so the
bundles are CI-verified but have never been launched by a person. Linux is in the same
position as before — built and inspected on a real Ubuntu host, but not installed on a
desktop by a person for this release.

## Known limitations

- **Unsigned builds.** Windows SmartScreen and macOS Gatekeeper warn on first launch, and
  macOS requires the System Settings approval described above. Code signing and
  notarization need an Apple Developer Program membership and a Windows certificate; both
  are backlog items, not v0.5.0.
- **macOS and Linux are beta.** **Verified structurally, not on a live machine** on
  macOS, and not re-verified by hand on a Linux desktop for this release. Windows remains
  the primary, hand-verified platform.
- **macOS updates are manual** until a stable signing identity exists (see above).
- **The first update cycle is still unproven.** `v0.5.0` is the first published feed, so
  no earlier install can have upgraded through it. The download → restart → install path
  gets its first real test at the next release (Windows and Linux AppImage; macOS stays
  manual).
- **Ubuntu 24.04+ dependency naming.** The `.deb` depends on `libasound2t64 | libasound2`
  to cover both the 24.04 rename and older releases; distributions with neither name fail
  the install with a dependency error.
- **AppImage updates** require the desktop to set `APPIMAGE`, which is standard for
  AppImageLauncher and most menus but not universal; the `.deb` install never
  self-updates.

## Upstream

The app pins `@earendil-works/pi-coding-agent` 1.4.0 and ships Node 24 as its bundled
runtime. Pi's `SettingsManager`/`SessionManager` write non-atomically, so a crash during
Pi's own flush can truncate `settings.json` or a session JSONL; the pinned SDK cannot be
patched. All SDK contact stays in `src/host/sdk/*`, which is what keeps an upgrade to one
directory.
