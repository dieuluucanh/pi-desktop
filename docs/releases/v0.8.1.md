# Pi Desktop v0.8.1

**Release date:** 2026-11-08 · **Status:** published to GitHub Releases by
`.github/workflows/release.yml` on tag `v0.8.1` · **Pi SDK:**
`@earendil-works/pi-coding-agent` 1.4.0 · **Bundled runtime:** Node 24.22.2

Pi Desktop is a standalone desktop app for the [Pi coding agent](https://pi.dev):
projects, sessions, chat, providers, models, extensions, packages, skills, themes and
settings in a UI, using the **same `~/.pi/agent` profile as terminal Pi**, so the two are
interchangeable. **Pi for Office is an optional integration**, not a built-in surface.

This is the fifth public release. It is a **stability release for the Linux packages**
and for the release pipeline itself. The v0.8.0 Linux builds shipped a `node-pty` binary
compiled on a 26.04-era runner that needed **glibc 2.42**, so the integrated terminal
could not start on any older distribution (Mint 22 / Ubuntu 22–24 / Debian 12). v0.8.1
builds that binary in a pinned Debian 11 container, refuses to package a binary above the
support floor, and opens a real PTY from the packaged artefacts in CI. There is no
feature change relative to v0.8.0.

## Install

Download from [GitHub Releases](https://github.com/dieuluucanh/pi-desktop/releases).

| Platform      | Artefacts                                                                                                            | Status  |
| ------------- | -------------------------------------------------------------------------------------------------------------------- | ------- |
| Windows (x64) | `Pi-Desktop-0.8.1-win-x64-setup.exe` (NSIS), `Pi-Desktop-0.8.1-win-x64-portable.exe`                                 | primary |
| Linux         | `Pi-Desktop-0.8.1-linux-x86_64-appimage.AppImage`, `Pi-Desktop-0.8.1-linux-amd64-deb.deb` (x64) and the `arm64` pair | beta    |
| macOS         | `Pi-Desktop-0.8.1-mac-arm64.dmg`, `Pi-Desktop-0.8.1-mac-x64.dmg` (plus the `.zip` pair used by the updater)          | beta    |

Builds are **unsigned**. Windows SmartScreen warns on first launch (**More info → Run
anyway**). macOS additionally requires an explicit approval:

1. Open the `.dmg` and drag **Pi Desktop** into `/Applications`.
2. Launch it once. macOS refuses, and there is no right-click override any more.
3. Open **System Settings → Privacy & Security**, scroll to the bottom, and choose
   **Open Anyway** for Pi Desktop.

If the bundle reports that it is **damaged** instead (usually after unzipping the `.zip`
rather than mounting the `.dmg`), clear the quarantine flag and try again:

```bash
xattr -dr com.apple.quarantine "/Applications/Pi Desktop.app"
```

On Linux, the AppImage needs FUSE (`libfuse2`, or run with `--appimage-extract-and-run`);
install the `.deb` with `sudo apt install ./…deb` rather than `dpkg -i` so the
GTK/NSS/asound dependencies resolve. The app bundles its own Node runtime: no system
Node, npm or Pi install is needed.

## What changed since v0.8.0

### The Linux terminal loads on older distributions again

`node-pty@1.1.0` publishes no Linux prebuild, so the Linux jobs compile it. In v0.8.0
that compile happened on `ubuntu-latest`, which by then resolved to a 26.04-era image:
the packaged `pty.node` required **glibc 2.42** and the host exited 1 before the terminal
could answer anything. On Mint 22.3 (glibc 2.39) the terminal host died silently on every
open.

The binary is now built by `npm run pty:linux -- --arch <x64|arm64>` inside a
**digest-pinned `debian:bullseye` container** (glibc 2.31, GCC 10 →
`GLIBCXX_3.4.28`) and written to `node_modules/node-pty/prebuilds/linux-<arch>/pty.node`,
with a `BUILD-INFO.json` recording the node-pty version, the bundled Node, the image
digest and the measured floor. `node_modules/node-pty/build` is deleted afterwards, because
node-pty's loader checks `build/Release` before `prebuilds/` and an unpinned runner build
would otherwise win.

The floor is now enforced, not documented:

- `afterPack` runs `readelf --version-info` and **fails the package** when the binary
  needs more than the floor, when no usable binary for the target survives the prune, when
  `out/host/terminal.mjs` is missing, or when a Linux tree still carries
  `build/Release/pty.node`.
- The Linux runners are pinned to `ubuntu-24.04` / `ubuntu-24.04-arm` instead of
  `-latest`.
- `scripts/verify-packaged-terminal.mjs` opens a **real PTY from the packaged app** — the
  unpacked tree, the extracted `.deb` and the AppImage — and once more inside Debian 11
  with the app's own bundled Node, which is the only place a floor mismatch cannot hide.
  It runs in every release job.
- `checks.yml` loads `node-pty` immediately after `npm ci`, so an `allowScripts` policy
  change is a red job instead of a Linux package whose terminal cannot start.

### A failed native load is diagnosable instead of fatal

`pty-node.ts` now imports `node-pty` **lazily, on the first request**, so a broken binary
cannot kill the host before it answers. On failure it probes each loader candidate
(`build/Release`, `build/Debug`, `prebuilds/<platform>-<arch>`) and keeps the **first real
dlopen error** — node-pty itself only reports the last candidate, which is why v0.8.0's
failure looked like a missing file rather than `version 'GLIBC_2.42' not found`.

- `terminal.open` answers a typed `native_unavailable` error and the host stays up; a new
  `terminal.info` request reports each candidate path with its own loader error.
- The supervisor keeps a bounded stderr ring, rejects pending requests on a spawn error and
  appends every `[terminal]` line to `<profile>/logs/terminal.log`.
- The tab's error banner keeps one actionable sentence and a **Details** disclosure with
  the per-candidate report and **Copy details**; **Diagnostics → Terminal** shows the same
  state, the last exit and the log path.
- Spawned shells strip `LD_LIBRARY_PATH` entries pointing into the AppImage mount, so the
  AppImage's own loader path cannot leak into the user's shell.

### Release tooling

The first v0.8.0 tag run failed after `prepare`: all four build jobs died within 43
seconds on upstream GitHub 504s, because electron-builder's built-in retry window is only
about 12 seconds. The rerun published v0.8.0, but the pipeline no longer depends on that
luck:

- `scripts/package-retry.sh` retries electron-builder three times (60 s, 120 s, cleaning
  `release/` between attempts); `scripts/retry.sh` does the same for `npm ci`,
  `gh release create` and `gh release upload`.
- `scripts/fetch-retry.mjs` retries `runtime:fetch` on 408/425/429/5xx and network errors,
  honours `Retry-After`, bounds each attempt, and cleans its staging tree on failure.
- The workflow caches the verified Electron zips and builder tools (**never**
  `node_modules` or `~/.npm`), sets `DEBUG=@electron/get:*`, pins `setup-node` to the
  runtime's 24.22.2, adds per-job timeouts (10/60/60/90/15 min) and retries the draft
  create, the publish flip and the anonymous feed probes.
- npm 12 blocks dependency install scripts by default; `package.json` carries an explicit,
  version-pinned approval for `node-pty@1.1.0`, guarded by
  `tests/packaging/native-install.test.ts`.

The runbook for a failed tag is documented in
[release-pipeline.md](../architecture/release-pipeline.md): rerun on a transient failure,
cut a **new patch** on a deterministic one, and never move a tag.

## Known limitations

- **Unsigned builds.** Windows SmartScreen and macOS Gatekeeper warn on first launch, and
  macOS requires the System Settings approval described above. Code signing and
  notarization need an Apple Developer Program membership and a Windows certificate; both
  are backlog items.
- **macOS and Linux are beta.** **Verified structurally, not on a live machine** on
  macOS, and not re-verified by hand on a Linux desktop for this release. Windows remains
  the primary, hand-verified platform.
- **macOS updates are manual** until a stable signing identity exists (see above).
- **The Linux native terminal is built for glibc 2.31 / `GLIBCXX_3.4.28`** (Debian 11 /
  Ubuntu 20.04) on both architectures. Distributions older than that floor are not
  supported; a binary above the floor is now a packaging failure. The `.deb` does not
  self-update — reinstall it.
- **The terminal needs a real PTY.** It is a local shell only: no remote/SSH session, no
  tmux control mode, no session recording and no docked split panel. Terminals in an
  untrusted project do not spawn until you grant trust, and a terminal tab holds one
  shell.
- **Linux arm64 still compiles at release time.** There is no upstream `node-pty`
  prebuild for Linux, so both arches are built in the pinned container during the release
  run and take about a minute each.
- **Informational notifications start hidden.** A useful `info` message — including the
  app's own checkpoint confirmations — needs the **Informational messages** class enabled
  in Settings → Notifications. Hidden rows are never lost: **Show hidden (N)** recovers
  them. The update offer is in-app only (bell row, toast and the About & updates dot).
- **AppImage updates** require the desktop to set `APPIMAGE`, which is standard for
  AppImageLauncher and most menus but not universal.
- **Nested repositories stay invisible in Changes.** Deliberate, documented parity with
  VS Code; the Explorer still sees them.
- **i18n, MCP and multi-window** remain deferred backlog, as recorded in
  [`product/backlog.md`](../product/backlog.md).

## Upstream

The app pins `@earendil-works/pi-coding-agent` 1.4.0 and ships Node 24.22.2 as its
bundled runtime. Pi's `SettingsManager`/`SessionManager` write non-atomically, so a crash
during Pi's own flush can truncate `settings.json` or a session JSONL; the pinned SDK
cannot be patched. All SDK contact stays in `src/host/sdk/*`, which is what keeps an
upgrade to one directory. The terminal host deliberately imports no SDK code and is a
separate build input, and `node-pty` is imported only by `src/host/pty-node.ts`.
