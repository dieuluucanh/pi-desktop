**Release date:** 2026-09-21 · **Status:** release candidate (manual acceptance
matrix pending) · **Pi SDK:** `@earendil-works/pi-coding-agent` 0.85.1 ·
**Bundled runtime:** Node 24

Pi Desktop is a standalone desktop app for the [Pi coding agent](https://pi.dev):
projects, sessions, chat, providers, models, extensions, packages, skills, themes
and settings in a UI, using the **same `~/.pi/agent` profile as terminal Pi**, so
the two are interchangeable. **Pi for Office is an optional integration**, not a
built-in surface.

This is the first tagged release: the MVP scope of the core-first plan
(steps 1–26) is frozen, with the release-candidate hardening of step 27.

## Install

Download the asset for your platform from the GitHub Release.

| Platform | Artefacts                                                                                                            | Status  |
| -------- | -------------------------------------------------------------------------------------------------------------------- | ------- |
| Windows  | `Pi-Desktop-0.1.0-win-x64-setup.exe` (NSIS), `Pi-Desktop-0.1.0-win-x64-portable.exe`                                 | primary |
| macOS    | `.dmg`, `.zip` (arm64 + x64)                                                                                         | beta    |
| Linux    | `Pi-Desktop-0.1.0-linux-x86_64-appimage.AppImage`, `Pi-Desktop-0.1.0-linux-amd64-deb.deb` (x64) and the `arm64` pair | beta    |

Builds are **unsigned** in v0.1.0. Windows SmartScreen and macOS Gatekeeper will
warn on first launch; the guide has the per-platform steps (including the Linux
FUSE and `apt install ./…deb` notes). The app needs no pre-installed Node and no
pre-existing Pi — the runtime is bundled.

Installed builds check GitHub Releases after launch and show an update banner
(**Download** → **Restart & install**). Updates never download on their own.

## Highlights

- **Projects and sessions** — open a folder, manage recents and trust, run
  parallel sessions in tabs, each in its own Pi host process; fork, clone, tree
  navigation, rename, OS-trash delete and HTML export.
- **Chat** — streaming text, thinking, tool cards with diffs, steering and
  follow-up while streaming, `Esc` to stop, compaction, context-usage ring,
  token/cost totals, 10k-entry virtualized transcript.
- **Context and commands** — `/` commands (app, extension, prompt, skill), `@`
  files, image paste/drop, `#` Office document mentions.
- **Providers and models** — OAuth subscriptions, write-only API keys, custom
  gateways (`models.json`), model/thinking pickers, favourites, per-project
  defaults, proxy/offline.
- **Extensions and packages** — the same discovery as terminal Pi, with
  provenance, load-error diagnostics, enable/disable, reload, install consent,
  the full `ExtensionUIContext` (dialogs, notifications, status, widgets,
  autocomplete providers) and the TUI rendering surface for `ctx.ui.custom()`,
  footers/headers, custom editors and extension renderers.
- **Settings** — every key in Pi's `docs/settings.md`, global and per project,
  with a raw JSON editor, diff, backups and external-edit detection.
- **Optional web tabs** — Plannotator and other localhost UIs open in isolated
  in-app tabs (no preload, sandboxed, permissions denied).
- **Recovery and safety** — safe mode, crash/timeout recovery from JSONL, a
  redacted diagnostics bundle, sandboxed renderer with a strict CSP, allowlisted
  IPC, telemetry off by default.
- **Onboarding** — welcome → profile choice (share `~/.pi/agent` or keep it
  private) → provider sign-in → project → optional recommended extensions →
  optional Office setup → first session. Every step is skippable.

The feature-by-feature comparison with terminal Pi is
[`../product/parity.md`](/product/parity/).

## Known limitations

Everything below is a real, user-visible limitation of v0.1.0, not a claim that
the feature is missing. The automated suite covers the logic; the items marked
"unverified on a real machine" need hardware/providers the CI run does not have,
and are the manual acceptance matrix in step 27 of the plan.

### Platform and distribution

- **Unsigned builds.** SmartScreen/Gatekeeper warnings on first launch; signing
  and notarization are deferred ([backlog](/product/backlog/)).
- **macOS and Linux are beta.** Both are produced by the same
  `electron-builder` configuration and the runtime lock includes their Node
  artefacts. The Linux `AppImage` and `.deb` (x64 + arm64) were built and
  inspected on a real Ubuntu host for this release — deb control metadata,
  contents, the bundled Node runtime, and the packaged `pi`/`node` shims and host
  bundle actually starting (`0.85.1`) — and CI builds them on demand via
  `release-linux.yml`. What has **not** been exercised is a real _install and
  first session_ on a Linux desktop (launcher entry, window association,
  provider sign-in), and macOS has not been built here at all. Windows remains
  the verified target.
- **The Windows installer builds, but has not been installed on a clean VM.**
  `npm run package:win` produces both artefacts with URL-safe, target-distinct
  names and the update feed (`latest.yml`) matches the setup file. The clean-VM
  install and first session remain the step-27 manual gate. `electron-builder.yml`
  is also pinned by `tests/packaging/builder-config.test.ts` (targets,
  `extraResources`, `asarUnpack`, the names, the GitHub feed).
- **The updater is verified against the policy and a fake port.** A real
  round trip against a published GitHub Release feed (download → restart →
  install) has not been run.

### Verified structurally, not on a live machine

- **Provider sign-in** (OAuth device/code flows) against real providers; the
  request/response plumbing and redaction are unit-tested.
- **Extension UI fidelity**: a real extension's `notify`/`status`/`widget`,
  `ctx.ui.custom()` overlays, footers/headers/custom editors and custom
  `renderCall`/`renderResult` renderers in the packaged app. The host emulation
  is tested with Pi's real components; the packaged rendering is not.
- **Office**: the whole wizard acceptance row (detect → install → sideload →
  verify; cancel leaving no partial registry value; uninstall restoring the
  previous state) and the bridge end to end (a real pane attached,
  `document:"active"` following focus, `#name` routing). Automated tests use
  scripted `/health` and fake runners.
- **Plannotator review round trip**: `/plannotator-plan-mode` → the review
  opening in-app → approve/deny returning control. The in-app tab machinery is
  tested; no real `plannotator` binary or provider run was involved.
- **Web-tab isolation on a loaded page**: the tests assert the view is created in
  the isolated partition with no preload, `sandbox`, `contextIsolation` and
  permissions denied — not that a real page proves `window.pi` is absent.
- **Reliability**: crash/timeout banners against a real wedged host, safe mode
  against a profile that really contains a broken extension, and the diagnostics
  bundle from a real run with real credentials in `auth.json`.
- **Performance**: 60 fps is asserted structurally (bounded DOM + full scroll
  height), not by frame timing; the 8-host RSS budget and 1.5 GB restart
  threshold use injected samples; the "50 MB tool result" path is tested just
  over the 1 MB spill threshold.
- **Sessions and projects**: `shell.trashItem` landing a session in the OS trash
  on each platform; the live trust round trip against a real `.pi/settings.json`;
  the external-editor launch.
- **Onboarding** against real providers and a real Office install.

### Upstream (not fixable in this app)

- **Pi's own writers are not crash-atomic.** `SettingsManager` writes
  `settings.json` with `writeFileSync`, and `SessionManager` appends/rewrites
  session JSONL with `appendFileSync`/`writeFileSync`. The app cannot patch the
  pinned SDK, so a crash _during Pi's own flush_ can still truncate those files.
  The app's own profile writes are atomic and now `fsync` before the rename.
- **MCP is parity, not a built-in.** Like terminal Pi, MCP is reached through an
  installed extension; there is no first-party bridge
  ([backlog](/product/backlog/)).
- **Backups cover `settings.json`**, not every profile file. `models.json`
  (custom providers), `keybindings.json` and imported themes are written
  atomically but are not backed up before the first app write.

### Deliberately deferred

See [`../product/backlog.md`](/product/backlog/) for the full list with
reasons: in-app terminal tab, native Plan/Review workspace, SQLite session
index/search, i18n, git worktrees, first-party MCP bridge, multi-window/scheduled
tasks/cloud sessions, code signing, and the external-editor launcher.

## Data, privacy and updates

- The app shares `~/.pi/agent` by default (settings, `auth.json`, sessions,
  extensions, packages). The onboarding profile step can keep a private profile
  under `userData` instead; the choice applies on the next launch.
- **Telemetry is off unless explicitly enabled.** The app sets
  `PI_TELEMETRY=0` for every host unless the preference is on, and never rewrites
  the shared `settings.json` for it.
- `auth.json` is Pi's and written `0600`; no IPC channel returns credential
  material, and the diagnostics bundle is redacted.
- Writes to the profile go through Pi's SDK managers or the app's atomic helpers
  (temp file → `fsync` → rename). A malformed `settings.json`, `auth.json` or
  `app-state.json` is reported and left untouched, never repaired silently.

## Verification status

- **Automated (green on the release commit):** `format:check`, `typecheck`,
  `lint`, `test` (unit + renderer), `test:coverage` (floors enforced), `build`,
  `e2e:smoke`, `e2e:perf`, `runtime:verify`, `office:manifest:check`, the
  packaging config guard, and a local `npm run package:win` that produced both
  Windows artefacts.
- **Linux packaging (verified on a real Ubuntu 26.04 host):**
  `electron-builder --linux --x64 --arm64` produced all four artefacts, each
  carrying the bundled Node runtime for its architecture. The `.deb` control
  metadata (name, version, architecture, maintainer, depends), its file list
  (bundled runtime, host bundle outside the asar, `.desktop` entry) and the
  AppImage payload were inspected, and the packaged `pi` / `node` shims plus the
  host bundle were run with `PATH` stripped to the shim directory — the host
  reports `0.85.1`. `latest-linux.yml` and `latest-linux-arm64.yml` name their
  own artefacts and do not collide.
- **Manual (the release gate):** the step-27 acceptance walkthrough on a clean
  Windows machine with real providers and a real Office install
  ([plan §Manual acceptance walkthrough](https://github.com/dieuluucanh/pi-desktop)
  is the design authority; the walkthrough is recorded with the release).
  Installing the Linux artefacts on a real desktop is the equivalent gate for
  Linux. The known-limitations list above is the honest state until those runs
  are complete.
